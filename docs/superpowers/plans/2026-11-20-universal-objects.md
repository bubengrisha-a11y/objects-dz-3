# Универсальный сервис объектов — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Статус:** утверждён агентом по поручению пользователя (пробный прогон задания автором курса).
Метод исполнения — subagent-driven, как требует задание.

**Goal:** один HTTP-сервис расширения `СчетаМагазина`, который описывает, ищет, читает и
создаёт справочники и документы любого вида; счёт покупателю создаётся через `POST /object`.

**Architecture:** HTTP-сервис — транспорт: параметры, разбор тела, права, транзакция, коды
ошибок. Общий модуль `СчетаМагазинаМетаданные` — всё о типах: поиск типа по имени и по слову,
описание полей по метаданным. Общий модуль `СчетаМагазинаДанные` — всё о данных: строгие
преобразования значений, поиск, заполнение и чтение объекта. Модули сервиса счетов
обобщаются на месте (подход 1 спецификации), XML метаданных не меняется.

**Tech Stack:** BSL платформы 8.5.1, выгрузка Hierarchical XML, REST Client,
BSL Language Server 1.0.7 для статической проверки.

**Spec:** [docs/superpowers/specs/2026-11-20-universal-objects-design.md](../specs/2026-11-20-universal-objects-design.md)

## Global Constraints

- Расширение `СчетаМагазина`, префикс `СчетаМагазина`; основная конфигурация не меняется.
  XML расширения не меняется: правятся только три модуля BSL, `src/tests/objects.http`,
  `src/tests/.env`, `README.md`.
- Маршруты и обработчики не меняются: `/types` → `НайтиТипы`, `/type` → `ОписатьТип`,
  `/search` → `НайтиОбъекты`, `GET /object` → `ПрочитатьОбъект`, `POST /object` → `СоздатьОбъект`.
- BSL и XML — UTF-8 с BOM и CRLF. Перед каждым коммитом: `python3 tools/bsl-check.py --fix`,
  ожидается последняя строка `OK: синтаксических ошибок нет, кодировка и переводы строк в порядке`.
- Ответы — через существующие `ОтветJSON` / `ОшибкаJSON` / `ОтказJSON`: JSON UTF-8 без BOM,
  `Content-Type: application/json; charset=utf-8`; ошибка —
  `{"error": {"code", "message", "details": [{"path", "message"}]}}`.
- Статусы и коды — только из таблицы «Ошибки и журнал» спецификации: `400 bad_request`,
  `400 unsupported_type`, `403 forbidden`, `404 type_not_found`, `404 not_found`,
  `415 unsupported_media_type`, `422 validation_failed`, `500 internal_error`.
- Привилегированный режим не включается; запросы к данным — `РАЗРЕШЕННЫЕ`; в текст запроса
  попадает только `Мета.Имя` объекта, найденного в метаданных; строка поиска — параметром через
  `ОбщегоНазначения.СформироватьСтрокуДляПоискаВЗапросе` и `СПЕЦСИМВОЛ "~"`.
- Не вызывать `Заполнить()` и обработку заполнения, не ставить `ОбменДанными.Загрузка`;
  документ записывается `РежимЗаписиДокумента.Запись`.
- Каждый обработчик ловит исключение и отдаёт его в `НепредвиденнаяОшибка` (`403` при
  нарушении прав, иначе журнал регистрации «СчетаМагазина» и `500`).
- В `objects.http` адрес, авторизация и UUID — только `{{$dotenv …}}`; имена именованных
  запросов (`# @name`) — латиницей.
- Комментарии в коде — по-русски и редкие, как в существующих модулях.
- Интерпретатора BSL вне базы нет. «Проверено» пишется только после загрузки в базу и
  запроса; до того — «статически проверено».

## Review Focus

1. Имя типа вида `Справочник.`, `.X`, `Справочник.А.Б`, `Catalog._ДемоПартнеры`,
   ` Справочник._ДемоПартнеры ` → `400` или `404`, не `500` и не в тексте запроса (Task 2).
2. Чтение объекта, где есть значения неподдерживаемых типов (ТЧ `ДополнительныеРеквизиты`,
   ссылки на планы видов характеристик) → `200` с `{"unsupported": true, "presentation"}`,
   не `500` (Task 4).
3. Ссылка на объект другого справочника, на группу, на помеченный на удаление или
   несуществующий объект → `400` с одним и тем же текстом без раскрытия (Task 5).
4. Отказ проверки заполнения → `422`, и в базе не появляется объект; исключение при записи
   откатывает транзакцию (Task 5).
5. `%`, `_`, `[`, `]` в строке поиска — обычные символы; `limit` `0`, `101`, `abc` → `400`;
   поиск по числовым коду или номеру с нецифровой строкой → `400`, а не сбой `ПОДОБНО` (Task 3).

## Проверка этапа

Тестов вне базы нет, поэтому «тест» этапа — запросы этапа в `objects.http` с ожидаемым
результатом. RED — до реализации маршрут отвечает `501` (стартовый набор). GREEN — после
загрузки: `tools\load-extension.cmd -InfoBase <каталог базы>` на компьютере с 1С, затем
запросы этапа в REST Client. Если исполнитель не может загрузить расширение, он пишет в
отчёте «загрузка и запросы не выполнены», а контроллер переносит проверку в журнал как
отложенную; статическая проверка её не заменяет.

### Task 5: POST /object — создание справочника и документа

**Files:** Modify: модуль Данные (`Подготовить`, `НовыйОбъект`, `Заполнить`, проверка ссылок);
HTTP-модуль (`СоздатьОбъект`, разбор тела, `ПутьПоля`, удалить `НеРеализовано`); Test: `objects.http`

**Interfaces:**
- Consumes: `НайтиТип`, `ИмяТипа`, `ЭтоСправочник`, `Схема`, `ТипыПоля`, `Прочитать`.
- Produces (Данные):
  - `Подготовить(Мета, Данные, Ошибки) Экспорт` → `Структура("header,tables")` из
    `Соответствие` с готовыми значениями 1С; `Данные` — тело целиком (`Соответствие`);
    все ошибки — в `Ошибки` через `Ошибка(Ошибки, Путь, Текст)`.
  - `НовыйОбъект(Мета) Экспорт` → `СоздатьЭлемент()` или `СоздатьДокумент()`.
  - `Заполнить(Объект, Подготовленные) Экспорт` — как в сервисе счетов.

- [ ] **Step 1: Запросы этапа** (тело — `Content-Type: application/json`)
  - `# @name newPartner` — справочник: `{"type": "Справочник._ДемоПартнеры", "header": {"Наименование": "Партнёр из REST Client", "ВидПартнера": "ЮридическоеЛицо", "Клиент": true}}` — `# Ожидается: 201; header.Код назначен 1С; header.ЭтоГруппа=false`

    `PRODUCT_ID`, `Количество` 1, `Цена` 1000, `Сумма` 1000, `Всего` 1000 —

## Особенности исполнения

Агент работает в песочнице Linux без платформы 1С и без сетевого доступа к опубликованной
базе пользователя, поэтому Step 6 задач 1–5 и Step 5 задачи 6 выполняет пользователь (или
агент, если база станет доступна по сети). Задача считается завершённой агентом после
ревью и статической проверки; отметка «проверено в базе» ставится только по результату
запросов. Отложенные проверки ведутся в журнале исполнения.

Проверка плана автором: разделы спецификации распределены — типы и `/types` (Task 1),
описание (Task 2), поиск (Task 3), чтение (Task 4), создание, ссылки, группы и проверка
заполнения (Task 5), приёмка (Task 6); интерфейсы задач согласованы по именам; пять пунктов
Review Focus закреплены запросами в задачах 1–5.
