# Универсальный HTTP-сервис объектов 1С

Статус: утверждена агентом по поручению пользователя. Пользователь — автор курса, делает
пробный прогон задания и поручил агенту все решения, которые ТЗ оставляет исполнителю,
без обсуждения. Такие решения помечены «Решение агента» и собраны в отдельном разделе,
чтобы их можно было проверить и переиграть.

Источник требований — ТЗ задания `tz-universal-service.md`. Образец процесса и правил —
[спецификация](2026-10-25-shop-invoices-design.md) и
[план](../plans/2026-10-25-shop-invoices.md) сервиса счетов с занятия. Ссылки этих
документов на `AGENTS.md`, выгрузку `1c/config`, CLI стенда и Node-тесты к этому
репозиторию не относятся: таких файлов здесь нет.

## Назначение

Сервис счетов работает, но следом пришли просьбы: магазину — заводить партнёров, складу —
оформлять поступления, внешней бухгалтерии — читать реализации. Отдельный сервис на каждую
просьбу дорог: описание, поиск и запись у них одни и те же. Нужен один сервис, который
описывает, ищет, читает и создаёт справочники и документы любого вида конфигурации; счёт
на оплату покупателю становится частным случаем.

Клиенты — разработчики внешних систем и их ИИ-ассистенты. Мерило полноты описания:
ассистент без документации по конфигурации сам находит тип по слову, узнаёт поля и
собирает тело запроса.

## Цели, не-цели, анти-цели

Цели: пять маршрутов ТЗ; справочники и документы с табличными частями; значения — строка,
число, дата, булево, ссылка на справочник или документ, перечисление; правила сервиса
счетов для любого типа: описание по метаданным, проверка заполнения перед записью,
документ — непроведённым, ограниченный поиск с признаком «найдено не всё», ошибки клиента
отдельно от сбоев 1С, формат обмена. Сервис счетов заменяется: счёт создаётся
через `POST /object`.

Не-цели. По ТЗ: изменение и удаление объектов, проведение; регистры, константы, отчёты,
обработки, планы видов характеристик и другие виды метаданных; дополнительные реквизиты и
сведения БСП; общие реквизиты конфигурации. Решение агента: создание групп справочников,
постраничная выдача, отбор поиска по владельцу, частичный поиск по числовым коду и номеру.

Анти-цели — провал, даже если сервис формально отвечает:

- обход штатной проверки заполнения, запись с флагом обмена, привилегированный режим;
- `500` там, где клиент прислал неверные данные или попросил неподдерживаемое;
- пользовательская строка (имя типа, строка поиска) в тексте запроса 1С;
- перечень полей конкретных объектов в коде: всё описание — по метаданным;
- молчаливое округление чисел, обрезание строк, преобразование строк в числа и булевы.

## Ограничения

- Конфигурация — демо БСП 3.2.1 (база `1Cv8_demo.dt`), платформа 8.5.1.960 или новее,
  режим совместимости расширения не выше конфигурации (сейчас `Version8_5_1`, не менять).
- Доработка — в расширении `СчетаМагазина` (префикс имён объектов `СчетаМагазина`);
  основная конфигурация не меняется. HTTP-сервис уже на корне `objects`, маршруты и
  обработчики заведены: `НайтиТипы`, `ОписатьТип`, `НайтиОбъекты`, `ПрочитатьОбъект`,
  `СоздатьОбъект`. Маршруты и имена обработчиков не меняются.
- Исходники — выгрузка Hierarchical XML в `src/extensions/СчетаМагазина/`; файлы BSL и
  XML — UTF-8 с BOM и переводами строк CRLF, как их выгружает Конфигуратор.
- Проверка — на своей базе, опубликованной на веб-сервере, запросами REST Client из
  `src/tests/objects.http`; адрес и авторизация — только в `src/tests/.env`.
  Интерпретатора BSL вне базы нет: до загрузки в базу код проверяется только статически.

## Рассмотренные подходы

1. **Обобщить существующие общие модули на месте. Решение агента.**
   `СчетаМагазинаМетаданные` и `СчетаМагазинаДанные` принимают метаданные типа вместо
   жёсткого `Документ()`. Проверенная на занятии логика — строгие преобразования значений,
   поиск с экранированием, транзакция с проверкой заполнения — сохраняется. Новых объектов
   метаданных нет, значит, нет и новых UUID в XML, которые до конца работы не проверить
   загрузкой. Минус — исторические имена модулей при универсальном содержимом.
2. Новые общие модули с универсальными именами и удаление старых. Имена чище, но
   добавляются XML-объекты и правки `Configuration.xml` и `ConfigDumpInfo.xml`, а код
   тот же. Не выбран: риск без выгоды для клиента.
3. Отдельные ветки кода для справочников и документов. Каждая ветка проще, но описание,
   преобразование и запись дублируются — ровно то, от чего уходит ТЗ. Не выбран.

## HTTP-контракт

Пути — относительно корня сервиса `…/hs/objects`. Ответы — JSON в UTF-8 без BOM,
`Content-Type: application/json; charset=utf-8`. Доступ — обычная аутентификация
HTTP-сервиса учётной записью 1С с её правами; привилегированный режим не включается;
запросы к данным — с `РАЗРЕШЕННЫЕ`.

| Маршрут | Назначение | Успех |
| --- | --- | --- |
| `GET /types?q=<слово>` | Найти типы по слову | `200` |
| `GET /type?name=<Вид.Имя>` | Описать тип | `200` |
| `GET /search?type=<Вид.Имя>&q=<строка>[&limit=<N>]` | Найти объекты типа | `200` |
| `GET /object?type=<Вид.Имя>&id=<uuid>` | Прочитать объект | `200` |
| `POST /object` | Создать объект | `201` |

### Имя типа

`Справочник.<Имя>` или `Документ.<Имя>` — вид русским словом, имя как в метаданных.
Регистр имени не важен, в ответах — каноническое имя из метаданных.

- Параметр отсутствует, пуст или не в форме «Вид.Имя» — `400 bad_request`.
- Вид не «Справочник» и не «Документ» (`РегистрСведений.X`, `Catalog.X`) —
  `400 unsupported_type` с пояснением, что поддерживаются справочники и документы.
- Вид поддерживается, объекта нет: в GET-маршрутах — `404 type_not_found`,
  в теле `POST` — `400 bad_request` с путём `type`.
- Нет права «Чтение» на тип — `403 forbidden`; для `POST` — нет права «Добавление».
- В текст запроса 1С попадает только каноническое имя найденного объекта метаданных.

### GET /types?q=<слово>

`q` обязательна и непуста после удаления внешних пробелов. Совпадение — подстрока без
учёта регистра, «ё» равна «е», в имени объекта метаданных или в его синониме
(`Представление()`). Выдаются только справочники и документы, на которые у пользователя
есть право «Чтение»: сначала справочники, затем документы, внутри — по имени. Лимита нет:
видов в конфигурации конечное число. Ничего не найдено — `200` с пустым `items`.

```json
{"items": [{"name": "Документ._ДемоПоступлениеТоваров", "kind": "document", "title": "Демо: Поступление товаров"}]}
```

`kind` — `catalog` или `document`.

### GET /type?name=<Вид.Имя>

```json
{
  "name": "Справочник._ДемоПартнеры",
  "kind": "catalog",
  "title": "Демо: Партнеры",
  "hierarchy": "groups",
  "owners": [],
  "search": {"field": "Наименование", "match": "substring"},
  "fields": [],
  "tables": [],
  "rules": {}
}
```

- `hierarchy` и `owners` — только у справочников. `hierarchy`: `groups` — иерархия групп и
  элементов, `items` — иерархия элементов, `null` — без иерархии. `owners` — имена типов
  владельцев, `[]` — справочник не подчинённый.
- `search` — как ищет `/search`: `field` (`Наименование`, `Код` или `Номер`) и `match`
  (`substring` или `exact`); `null` — тип не ищется (нет наименования, кода, номера).
- Поле: `name`, `title`, `writable`, `required`, `types`; при `writable=false` — `reason`.
- Табличная часть: `name`, `title`, `writable`, `required` (нужна хотя бы одна строка),
  `fields`; при `writable=false` — `reason`. Стандартный реквизит `НомерСтроки` не
  описывается: номер строки — её позиция в массиве.
- `rules` — правила для ассистента текстом: окончательное решение об обязательности
  принимает штатная проверка заполнения; формат дат; смысл `null`; ссылки и поиск их
  значений; составные значения; запрет округления и обрезания.

Описание типа значения:

| `kind` | `name` | Дополнительно |
| --- | --- | --- |
| `string` | `string` | `length` (0 — неограниченная), `fixedLength` |
| `number` | `number` | `digits`, `fractionDigits`, `nonnegative` |
| `boolean` | `boolean` | — |
| `date` | `date` | `parts`: `date` или `dateTime` |
| `ref` | `Справочник.X` или `Документ.Y` | `searchUrl`: `/search?type=<name>` |
| `enum` | `Перечисление.Z` | `values`: `[{"name", "title"}]` |
| `unsupported` | представление типа 1С | — |

Дата только с частью «Время», ссылки на прочие виды объектов (планы видов характеристик и
т. п.), хранилище значения, уникальный идентификатор и любые другие типы — `unsupported`.
Поле, у которого хотя бы один тип `unsupported`, — `writable=false` с причиной.

Поле с несколькими типами — составное: пишется и читается как
`{"type": "<name из types>", "value": …}`. Решение агента: составные из поддерживаемых
типов поддерживаются, как в сервисе счетов (ТЗ разрешает их не поддерживать).

Обязательность (`required`): у реквизита и табличной части — их
`ПроверкаЗаполнения = ВыдаватьОшибку`; у стандартного реквизита — его
`ПроверкаЗаполнения`, кроме правил сервиса в таблице ниже.

Стандартные реквизиты описываются правилами сервиса, а не перечнем прикладных полей:

| Реквизит | Справочник | Документ |
| --- | --- | --- |
| `Ссылка` | не описывается: это `id` | не описывается: это `id` |
| `Код` | есть, если `ДлинаКода > 0`; запись — только при выключенной автонумерации, иначе «Код назначает 1С» | — |
| `Наименование` | есть, если `ДлинаНаименования > 0`; запись | — |
| `Родитель` | есть у иерархического; запись; см. «Группы» | — |
| `Владелец` | есть у подчинённого; запись; `required=true` | — |
| `ЭтоГруппа` | без записи: «Создание групп не поддерживается» | — |
| `Дата` | — | запись; `required=true` — правило сервиса |
| `Номер` | — | запись — только при выключенной автонумерации, иначе «Номер назначает 1С» |
| `Проведен` | — | без записи: «Сервис не проводит документы» |
| `ПометкаУдаления` и прочие | без записи | без записи |

Решение агента: у справочника с иерархией групп реквизиты и табличные части
с `Использование = ДляГруппы` — `writable=false` с причиной «Реквизит групп; создание
групп не поддерживается». Табличная часть БСП `ДополнительныеРеквизиты` — `writable=false`
с причиной «Дополнительные реквизиты и сведения БСП вне рамок сервиса».

### GET /search?type=<Вид.Имя>&q=<строка>[&limit=<N>]

`q` обязательна и непуста после удаления внешних пробелов. `limit` — только цифры,
целое от 1 до 100, по умолчанию 20. Символы шаблона `%`, `_`, `[`, `]` — обычные символы
(`ОбщегоНазначения.СформироватьСтрокуДляПоискаВЗапросе` и `СПЕЦСИМВОЛ "~"`). Запрос
выбирает не больше `limit + 1` строк, без помеченных на удаление.

- Справочник: по `Наименование` (подстрока), если `ДлинаНаименования > 0`; иначе по
  `Код`: строковый — подстрока, числовой — точное совпадение. Порядок — поле поиска, затем
  ссылка. Решение агента: группы входят в выдачу с признаком `isFolder`, чтобы клиент мог
  найти группу для `Родитель`.
- Документ: по `Номер`: строковый — подстрока, числовой — точное совпадение. Порядок —
  дата по убыванию, затем ссылка.
- Точное совпадение при `q`, которое не целое число, — `400 bad_request`. Тип с
  `search=null` — `400 bad_request` «Поиск по этому типу не поддерживается».

Элемент выдачи справочника: `id`, `code` (если есть код), `name` (если есть
наименование), `isFolder` (только при иерархии групп), `owner` (только у подчинённого:
UUID строкой; при нескольких владельцах — `{"type", "value"}`). Элемент выдачи документа:
`id`, `number`, `date`, `posted`.

```json
{"items": [{"id": "9203492b-ea3e-11de-8634-001d600d9ad2", "code": "000000001", "name": "Альфа", "isFolder": false}], "hasMore": false}
```

`hasMore=true` — найдено больше `limit`: уточните строку или увеличьте `limit`.

### GET /object?type=<Вид.Имя>&id=<uuid>

`id` — UUID строкой из 36 символов, регистр не важен; иначе `400 bad_request`. Объекта нет
или он недоступен пользователю — `404 not_found`, без раскрытия, какой из двух случаев.

```json
{
  "type": "Документ._ДемоСчетНаОплатуПокупателю",
  "id": "…",
  "header": {"Дата": "2026-11-20T10:00:00", "Номер": "…", "Проведен": false, "Партнер": "…"},
  "tables": {"Товары": [{"Номенклатура": "…", "Количество": 1, "Цена": 100, "Сумма": 100, "Всего": 100}]}
}
```

- `header` — все описанные поля, включая недоступные для записи, в формате значений
  записи. У группы справочника — поля с `Использование` «для группы» и «для группы и
  элемента», у элемента — «для элемента» и «для группы и элемента».
- `tables` — все табличные части с тем же учётом `Использование`; строки — массив объектов.
- Пустая ссылка и пустая дата — `null`. Значение неподдерживаемого типа —
  `{"unsupported": true, "presentation": "<представление>"}`. Решение агента: чтение не
  падает и не теряет информацию.

### POST /object

Тело — `Content-Type: application/json`, допустим `charset=utf-8`; иначе
`415 unsupported_media_type`.

```json
{"type": "Справочник._ДемоПартнеры", "header": {"Наименование": "ООО «Ромашка»", "ВидПартнера": "ЮридическоеЛицо", "Клиент": true}}
```

- `type` и `header` обязательны, `tables` — нет (объект «имя ТЧ → массив строк»).
  Неизвестные ключи верхнего уровня, неизвестные поля и табличные части, поля и табличные
  части с `writable=false` — `400` с путём.
- Документ без `header.Дата` или с `null` — `400` (правило сервиса).
- Порядок создания — как в сервисе счетов: полностью разобрать JSON с проверкой хвоста
  после значения; проверить структуру, поля и значения по описанию типа и подготовить
  значения с точными типами 1С, ничего не записывая; создать объект (`СоздатьЭлемент` или
  `СоздатьДокумент`) без обработки заполнения; перенести шапку и строки; в транзакции
  очистить сообщения, вызвать `ПроверитьЗаполнение()`, при отказе откатить и вернуть
  `422` со всеми сообщениями; записать (документ — `РежимЗаписиДокумента.Запись`, затем
  убедиться, что не проведён); зафиксировать. При исключении — откат.
- Ссылка указывает на существующий, доступный пользователю, не помеченный на удаление
  объект нужного типа. Ссылка на справочник с иерархией групп принимает только элемент,
  кроме `Родитель` (см. «Группы»). Ошибка не раскрывает, существует ли недоступный объект.
- Отказ уже при записи, после успешной проверки заполнения (обработчики объекта ставят
  `Отказ`, даты запрета изменения БСП и т. п.). Решение агента: если 1С оставила сообщения
  пользователю — `422 validation_failed` с этими сообщениями, пути — по тем же правилам;
  иначе нарушение прав — `403`, остальное — `500`. Транзакция откатывается в любом случае.
- Известное ограничение (решение агента): неуникальные `Код` или `Номер` при выключенной
  автонумерации и превышение числа уровней иерархии платформа отклоняет исключением без
  сообщений — это `500` с кратким текстом 1С. Сервис заранее их не проверяет: такие виды
  редки, а проверка уникальности номера с учётом периодичности документов не окупается.
- Успех — `201`, тело — как у `GET /object` для созданного объекта. Защиты от повторов
  нет: каждый успешный запрос создаёт новый объект.
- Дополнительные реквизиты БСП вне рамок. Если в базе для вида объекта настроены
  обязательные дополнительные реквизиты, создание вернёт `422` с сообщением БСП — это
  верное поведение: проверку сервис не обходит, настройки базы агент не меняет. Для
  контрольного примера тогда берётся другой вид объекта, а случай описывается в отчёте;
  менять настройки базы — только по решению пользователя.

### Значения JSON

| Тип | Передача |
| --- | --- |
| Строка | Строка JSON; длина не больше `length`, при `fixedLength` — ровно `length` |
| Число | Число JSON; разрядность, точность и знак проверяются, без округления |
| Булево | `true` или `false` |
| Дата | `YYYY-MM-DD` для части «Дата», `YYYY-MM-DDTHH:MM:SS` для «Дата и время»; зона и `Z` отклоняются |
| Ссылка | UUID строкой |
| Перечисление | Имя значения строкой |
| Составной тип | `{"type": "<name>", "value": …}` |

`null` — штатное пустое значение поля; у составного — `{"type": …, "value": null}`.
Обязательность проверяет 1С (кроме правил сервиса для `Дата` документа).

### Группы и подчинённые справочники

Решение агента (ТЗ оставляет исполнителю):

- Группы читаются (`header.ЭтоГруппа`) и находятся поиском (`isFolder`).
- Новый элемент можно поместить в существующую группу через `Родитель`. При иерархии
  групп `Родитель` принимает только группу того же справочника, при иерархии элементов —
  только элемент; помеченные на удаление не принимаются.
- Создание групп не поддерживается: `ЭтоГруппа` недоступно для записи, запрос с ним —
  `400` с причиной. Почему: у групп свой набор полей, а нужны они внешней системе редко;
  поместить нового партнёра в группу «Покупатели» — нужно часто.
- Подчинённые справочники поддерживаются: `Владелец` обязателен и пишется как обычная
  ссылка (при нескольких владельцах — составное значение), в поиске у элемента есть
  `owner`. Отбора поиска по владельцу нет: маршрут фиксирован.
- Ограничение числа уровней иерархии сервис заранее не проверяет; нарушение отклоняет
  платформа при записи.

### Ошибки и журнал

```json
{"error": {"code": "bad_request", "message": "Запрос не прошёл проверку", "details": [{"path": "header.ВидПартнера", "message": "…"}]}}
```

`path` — путь в запросе: `type`, `q`, `limit`, `id`, `header.<Поле>`,
`tables.<ТЧ>[<индекс с 0>].<Поле>` — или `null`. Ошибки значений собираются все сразу.

| Статус | `code` | Причина |
| --- | --- | --- |
| `400` | `bad_request` | Неверные параметры, JSON, структура, поле, тип значения, ссылка |
| `400` | `unsupported_type` | Вид метаданных не поддерживается |
| `403` | `forbidden` | Нет права на тип или операцию |
| `404` | `type_not_found`, `not_found` | Нет типа; нет объекта или он недоступен |
| `415` | `unsupported_media_type` | Тело не JSON |
| `422` | `validation_failed` | Штатная проверка заполнения или запись отказали с сообщениями 1С; ничего не записано |
| `500` | `internal_error` | Неожиданное исключение 1С; при создании транзакция отменена |

Сообщения проверки заполнения получают путь только при точном совпадении поля сообщения
с полем шапки (с префиксом `Объект.` или без) или со строкой табличной части
`<ТЧ>[<индекс>].<Поле>`; иначе `path=null`, текст — без угадывания. Нарушение прав —
`403`, иначе подробности сбоя — в журнал регистрации, событие `СчетаМагазина`, клиенту —
краткий текст. Тело запроса и авторизация в журнал не пишутся. Неподдерживаемые методы
и отказ аутентификации — в ведении платформы.

## Решения, которые ТЗ оставляет исполнителю

Все приняты агентом по поручению пользователя:

1. Форма JSON всех маршрутов — раздел «HTTP-контракт».
2. Группы — читаются и ищутся, элемент можно поместить в группу, создание групп — отказ.
3. Подчинённые справочники — поддерживаются через `Владелец`.
4. Составные типы из поддерживаемых — поддерживаются.
5. Неподдерживаемое значение при чтении — объект `unsupported` с представлением.
6. Поиск: `limit` 1–100 (20); документы — по номеру; числовые код и номер — точное
   совпадение; группы — в выдаче.
7. Ответ `POST` — полное чтение созданного объекта.
8. `Код` и `Номер` пишутся только при выключенной автонумерации.
9. Отказ при записи с сообщениями 1С — `422`; неуникальный код или номер и предел уровней
   иерархии — известное ограничение (`500` с текстом 1С).
10. Обязательные дополнительные реквизиты БСП не обходятся; контрольный пример при них —
    на другом виде объекта.

## Проверка и приёмка

- Статическая проверка исходников — до загрузки; она не заменяет проверку в базе.
- Каждый этап плана заканчивается загрузкой расширения в базу и запросами своего
  маршрута. Из среды агента база недоступна: загрузку выполняет пользователь скриптом
  `tools/load-extension.cmd`, запросы — REST Client; если опубликованная база станет
  доступна агенту по сети, запросы может выполнить и он.
- `tools/load-extension.cmd -InfoBase <каталог базы> [-User …] [-Password …] [-Platform …]`
  запускает Конфигуратор в пакетном режиме: загружает XML из `src/extensions/СчетаМагазина`
  в расширение (`/LoadConfigFromFiles … -Extension`), обновляет его в базе
  (`/UpdateDBCfg -Extension`) и выгружает `СчетаМагазина.cfe` в корень репозитория. Эталон
  исходников — репозиторий: обратной выгрузки в XML нет, XML расширения работа не меняет.
- `tools/bsl-check.py` — статическая проверка: синтаксис BSL (BSL Language Server) и
  кодировка файлов выгрузки (UTF-8 с BOM, CRLF).
- `objects.http`: по запросу на каждый маршрут; создание справочника (партнёр) и
  документа (счёт на оплату покупателю — тем же маршрутом); ошибки клиента — неизвестный
  тип, неподдерживаемый вид, `422` без обязательного поля. Адрес, авторизация и UUID —
  только переменные `.env`.
- Контрольный пример: созданные запросами партнёр и счёт открываются в 1С, счёт не
  проведён; скриншоты делает пользователь.
- Расширение выгружается в `СчетаМагазина.cfe` в корне репозитория.

## Демо-данные для примеров

Взяты из метаданных базы `1Cv8_demo.dt`.

- `Документ._ДемоСчетНаОплатуПокупателю`. Обязательные реквизиты: `Организация`
  (`_ДемоОрганизации`), `Партнер` (`_ДемоПартнеры`), `Ответственный` (`Пользователи`),
  `Подразделение` (`_ДемоПодразделения`), `ВалютаДокумента` (`Валюты`). ТЧ `Товары`:
  обязательны `Номенклатура`, `Цена`, `Сумма`, `Всего`; `Количество` — Число(15,3).
  `Контрагент` необязателен. UUID — в `.env`: `ORGANIZATION_ID`, `PARTNER_ID`,
  `RESPONSIBLE_ID`, `DEPARTMENT_ID`, `CURRENCY_ID`, `PRODUCT_ID`, `COUNTERPARTY_ID`.
- `Справочник._ДемоПартнеры`: иерархия групп и элементов, код 9 символов с
  автонумерацией, наименование 150. Обязателен `ВидПартнера` —
  `Перечисление._ДемоЮридическоеФизическоеЛицо`: `ЮридическоеЛицо`, `ФизическоеЛицо`.
  Булевы `Клиент`, `Поставщик`, `Конкурент`, `ПрочиеОтношения`; ТЧ `КонтактнаяИнформация`
  и `ДополнительныеРеквизиты`.
- Тип по слову «поступление» — `Документ._ДемоПоступлениеТоваров`; документы для
  бухгалтерии — `Документ._ДемоРеализацияТоваров`.

## Что остаётся исполнителю

Разбиение на процедуры и функции, внутренние структуры, тексты сообщений (коды и статусы
зафиксированы выше), состав `rules`, выбор демо-строк для примеров ошибок. Эти решения не
меняют контракт, не обходят штатную проверку и не добавляют операций.

После утверждения спецификации составляется план реализации.
